# P2 (hits measurable) and B1 (first live bridge): DESK, EnginePerf's side (2026-11-23)

Order: Overseer, after P1 was accepted. Desk only, no box until it rules. Joint with ITRZone: ITRZone writes the ITR2
side (receive, spawn and steer puppets, the player feed). This page is the X-Ray side, plus a transport proposal for
both of us to agree on.

## P2: P1 again with god mode OFF, damage neutralised, hits visible

### Mechanism (desk-checked in source and in P1's void run)
- Without g_god the actor_on_before_hit callback fires. In P1's void run my handler logged 107 hits with god mode off.
  With g_god on, the retry logged 0 (the engine skips the script callback).
- The damage itself comes from GAMMA's grok_actor_damage_balancer.script (run/ private copy, regular file, sha256 prefix
  467a21e263d10481, listed in run/private_copies_manifest.tsv). In its actor_on_before_hit it computes `damage`, prints
  "//Damage to actor = ...", sets shit.power = 0 and ret_value = false, then on line 751
  `actor:set_health_ex(actor.health - damage)` (line 747: on-before-death when the hit would kill).
- Test-only patch, in the run/ copy only, applied by the driver and restored after (pristine copy kept, hash checked
  before and after):
  ```lua
  -- P2 test patch (inert unless -p1_nodmg): damage computed and logged, not applied
  if p1_on_damage then p1_on_damage(shit, bone_id, damage) end
  if string.find(command_line(), "-p1_nodmg", 1, true) then return end
  ```
  inserted after `shit.power = 0`, before line 747. Effect: GAMMA still computes and prints the damage, the engine hit
  stays cancelled (the balancer's own ret_value = false), and health is not changed.
- p1_on_damage (a global set by zz_p1_puppet.script) writes "DMG,t,hitter_id,damage,bone" to meta. In P1, the
  power in h lines was often 0 because the balancer ran first and zeroed it. P2 takes the real damage from DMG lines.
  The export formats stay unchanged for ITRZone's scorer.
- Backup: the refill to 1.0 on every update stays. It covers what does not go through the balancer: radiation
  (70 of P1's 107 void-run hits were zone_field_radioactive_weak), bleeding and anomalies.
- Not touched: the engine, other scripts, and Caden's install. No g_god.

### Predictions (registered with the P2 prereg; from P1's data)
- Rate, from P1's void run (god mode off): 33 monster hits in the first 150 s of track, with 57.2 monster-seconds within
  3 m of the actor (572 o lines at 10 Hz), so 0.58 monster hits per monster-second of contact.
- P1 retry, full track: 98.1 monster-seconds within 3 m (981 o lines). Predicted P2 monster hits over the full track:
  about 57, range 20-120. Without death, mutants may stay longer, so the count could be higher.
- At least one h line with hitter_kind m: 95 %. Death: 0 (refill plus the patch): 90 %.
- Anomaly and radiation hits (hitter_kind x): >= 50 over the full track, 80 % (void run: 72 in its first 150 s).
- DMG lines = balancer hits (m plus s hits that pass through the balancer); every h line from m or s has a DMG line
  within the same frame: 85 % (handler order is not fixed, so a few may be split).

## B1: the first live link (X-Ray export -> running ITR2 puppets; ITR player -> X-Ray actor track)

### Transport: UDP on localhost (recommended), tmpfs file as the fallback
| Option | Wine here | Proton (Caden's play) | Across two prefixes / wineservers | Notes |
|---|---|---|---|---|
| UDP 127.0.0.1 | Winsock maps to Linux sockets | same | YES | One datagram per tick, non-blocking, no file growth. X-Ray side: LuaJIT ffi to ws2_32 (ffi compiled in, base.cpp:47); UNTESTED |
| tmpfs file (/dev/shm via Z:) | proven in P1 (10 Hz, 0.45 ms per tick) | Z: maps / by default; inside Steam's runtime container /dev/shm is very probably shared; NOT VERIFIED | YES | Needs a ring or overwrite scheme plus polling; adds up to one poll period of latency |
| Windows named pipe | works within one wineserver | same | NO | X-Ray and ITR2 run in different prefixes, so no |
Recommendation: UDP. The first test may use the tmpfs file, because that path is already proven on the X-Ray side.

### Messages
- X-Ray -> ITR2 at 10 Hz: one snapshot per tick. The header carries seq, the X-Ray time and the track/actor time. Then per
  online creature: id, section, kind, x, y, z, yaw (to add: o:direction()), health, best_enemy, and alive.
  Spawn/despawn = an id appearing in or missing from the snapshot (the same rule as P1's ON/OFF). At P1's peak there were
  76 creatures online, about 60 bytes each, so about 4.5 KB per snapshot: one datagram.
- ITR2 -> X-Ray at 20 Hz: seq, the player's x, y, z and yaw in X-Ray metres (ITRZone already has the coordinate
  transform from P1). X-Ray applies the latest pose at its next actor update (set_actor_position plus
  set_actor_direction), as P1's mover does today, but fed live instead of from the CSV.

### Latency budget (a target, not measured)
- Player -> X-Ray: send period 50 ms (25 ms average) + transport < 1 ms + up to one X-Ray frame (6-20 ms). About 40-75 ms.
- X-Ray -> ITR2 display: export period 100 ms (50 ms average) + 0.45 ms export + transport < 1 ms + up to one ITR2
  frame (11-17 ms at 60-90 fps) + interpolation buffer (one snapshot, 100 ms). About 160-270 ms.
- Proposed limits for B1: player -> X-Ray <= 100 ms; creature display <= 300 ms; both measured from the seq/time stamps
  on both sides.
- Open problem flagged now: melee. X-Ray decides a mutant's hit from a player pose about 40-75 ms old. ITR2 shows the
  attack about 160-270 ms after X-Ray decided it. Who owns melee hits (X-Ray or ITR2) is a design ruling, not a
  transport question. P2 measures what X-Ray sees.

### First tests (each with its own prereg; box time only on a ruling)
- B1-T0 (no X-Ray run): ITR2 replays P1's retry export (out/p1_retry/on/export_on.csv) and spawns and steers puppets on
  its floor. This tests the ITR2 side alone with known data. It is ITRZone's run.
- B1-T1 (one direction live): headless X-Ray runs the P1 track from the CSV and exports by UDP. ITR2 receives and shows
  the puppets. We measure the loss rate and the display latency from the stamps. Two engines at once: about 17 GB
  (X-Ray VmRSS, 3.5 GB private) plus ITR2. That needs a joint EXCLUSIVE slot, which is the Overseer's ruling.
- B1-T2 (both directions): the ITR2 player pose drives the X-Ray actor (the P1 mover fed live), and creatures chase a
  player who is in ITR2. The checks are P1's chase rule, now on ITR2's player.

### Unknowns

## Overseer rulings on B1 (2026-11-23)
1. Melee: near the player ITR2 owns all combat. X-Ray's hits on the actor are neutralised and ignored, and X-Ray learns only of
   creature deaths and of the player's position. This removes the old-pose melee problem.
2. P2 is DROPPED. It measured X-Ray's hits on the actor, which the hybrid ignores. The balancer patch (above) is kept on
   file in case the ruling changes, and also as the bridge's way to neutralise X-Ray damage without god mode.
   ITRZone's P2 predictions, recorded for completeness (never run): track 90 %, mesh 90 %, switch 70 %, chase 85 %,
   hits logged 85 %, hit count within 20-120 60 %.
3. Transport: UDP on localhost, tmpfs as the fallback. Prove UDP from Lua under Wine at the desk or in a tiny probe.
4. T0 is ITRZone's to run once its side is in. T1 and T2 wait for a ruling after T0.

## Transport, after both sides' facts: the FALLBACK (tmpfs files) applies for B1
- ITR2 side (ITRZone): the mod is UE4SS v4.0.0 Lua with plain io and os, and no sockets or ffi. UDP there would need a
  native module, which is a new install or build (security and the Overseer). So ITR2 uses files in both directions.
- X-Ray side, desk proof (source): LuaSocket IS compiled into the engine (3rd party/lua-extensions/luasocket, opened as
  "socket.core" plus gamedata socket.lua), and so is LuaJIT ffi. BOTH are opened ONLY when the console variable
  lua_debug = 1 when the script engine initialises (script_storage.cpp:458-470, base.cpp:43-48). Our user.ltx has
  lua_debug 0. lua_debug 1 also loads the kernel scripts global.lua and dynamic_callbacks.lua and initialises LuaPanda
  (a debugger), so its side effects on the headless server must be checked before use. UDP is therefore POSSIBLE
  on the X-Ray side but untested. It only matters if ITR2 ever gets sockets.
- X-Ray side, constraint: os.rename and os.remove are REMOVED from the game's Lua (disable_os_funcs,
  script_storage.cpp:318-329). So X-Ray cannot do ITRZone's "write snap.tmp, rename over snap.txt". Instead X-Ray
  rewrites snap.txt in place (open "w", write, close). ITRZone's reader already keeps a snapshot only when the header
  seq equals the "end,seq" line, so a torn or partly written file is rejected and the last good snapshot is kept. That
  makes the rename unnecessary. (With lua_debug 1, ffi MoveFileExW would give a real atomic replace, if we ever want it.)
- Formats (ITRZone): /dev/shm/itrz_b1/snap.txt = header `seq,t_xray,t_track`, one `o` line plus yaw and alive per creature,
  last line `end,seq`. /dev/shm/itrz_b1/pose.txt = ITR2 appends `seq,t,x,y,z,yaw` at 20 Hz; X-Ray tails it from its last
  offset at each update. The player's hits on puppets come back as `h,id,damage,bone` lines in the same file, and X-Ray
  applies them, so creature health and deaths stay in A-Life.
- Latency with files: X-Ray -> ITR2 is unchanged (10 Hz write; ITR2 polls every frame or 50 ms). Pose is 20 Hz
  appends; X-Ray reads them at each update (6-20 ms). The budget of section B1 still holds.

## ITRZone's ITR2 side (ITRZone's text, summarised; ITRZone owns it)
Puppets only within R_on 100 m of the player, despawned beyond R_off 150 m (the A1 rule), role-mapped classes (cats and
dogs -> Creep, boar and flesh -> CreepBig, snorks -> FragmentInvisible, zombies -> Mimic, Creep as the fallback). Steering:
an AI MoveTo toward the X-Ray position, with a teleport if the error is over 5 m or there is no path. Yaw comes from the
snapshot. The puppet's own attack is allowed only if X-Ray says best_enemy == actor and the distance is < 3 m. Health and
alive come from X-Ray. T0: P1's export preprocessed into per-tick snapshots and replayed at 10 Hz on Cordon. Checks:
puppets within 2 m of X-Ray's position at the 95th percentile, spawn and despawn at 100 and 150 m, no fall-through, frame
time against G3.
X-Ray work this implies for T1 (mine; built only after the T0 ruling): the snapshot writer (P1's export, plus yaw via
o:direction() and alive, in place with seq/end), the pose tailer replacing P1's CSV mover, applying h lines to creatures,
and the balancer patch made a bridge mode (X-Ray damage to the actor computed, logged and not applied).
